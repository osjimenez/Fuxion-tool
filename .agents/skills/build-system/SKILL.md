# Build system (packages, props and targets)

The Fuxion code lives in several repos mounted in the Fuxion workspace (the metarepo `Fuxion-workspace`): `oss/repo` (public,
must build **on its own**), `plus/repo`, `next/repo`, `archive/repo`, `lab/repo` and `tool/repo` (the tool and its SDK,
§9). Each has its solution at its root (`Fuxion.slnx`, `FxPlus.slnx`, `FxNext.slnx`…; design D-33) and its projects
under `solution/` (`src`, `test`). The workspace root has `Fuxion.slnx`, composed from the solutions of the repos and
versioned (generated by `fx sync` from the `solutions` of `_fx/dotnet/dotnet.yaml`). The design is
`_docs/plans/diseno-workspace-fx.md` (§6, §7); how it got here, plan N (phase 4) and its decisions 15-18, and plan P
(the layout of `_fx/` by modules, `_fx/.inherited/`, nested workspaces).

## 1. The pieces

| Where | What | Who writes it |
|---|---|---|
| `<repo>/global.json` | `msbuild-sdks: Fuxion.Tool.Sdk` (the version) and the test runner (Microsoft.Testing.Platform) | `fx sync` (the SDK version, from `dotnet.yaml`'s `sdks:`); the rest by hand |
| `<repo>/solution/**/Directory.Build.props` | `<Import Project="Sdk.props" Sdk="Fuxion.Tool.Sdk" />`, after the area's own properties | by hand |
| `<workspace>/_fx/dotnet/` (`dotnet.yaml` and its files) | **the shared build**: variables (frameworks, conditions, constants), imports (plain props/targets) and the shared package versions, for the repos of its `applies-to` (`tags: [fuxion-build]`); and the workspace's solution | by hand, in the workspace |
| `<repo>/_fx/.inherited/` | what the repo receives: `dotnet/` (the workspace's yaml, merged and without the solutions, and its files), `fx.yaml` (the catalog of tags) and `inherited.yaml` (who the repo is for its workspace, its parent, where each file comes from) | `fx sync`; **never edit** |
| `<repo>/_fx/dotnet/dotnet.g.props`, `dotnet.g.targets`, `packages.g.props` | what fx generates for this repo, from what it inherits and its own `_fx/dotnet/dotnet.yaml` | `fx sync`; **never edit** |
| `<repo>/solution/Directory.Packages.props` | this repo's own package versions (central package management) | by hand (and NuGet's UI) |

- Everything under `_fx/` of a repo is versioned, so a loose clone (oss on GitHub) builds the same without the
  workspace.
- **To change the shared build**, edit the workspace's `_fx/dotnet/dotnet.yaml` or its files, then `fx sync` (it gives
  every repo it applies to its `_fx/.inherited/`, and regenerates them). `fx doctor` checks everything is up to date.
- A repo can have its own `_fx/dotnet/dotnet.yaml` (and files in `_fx/dotnet/`): they add to what it inherits, and win
  by name. `oss` and `plus` have one, with `standalone: true`.

## 2. Fuxion.Tool.Sdk: only its own features (design D-37)

The SDK adds `Fx*` properties for the tool's features and decides nothing else (no language version, test framework or
packaging metadata: those are the shared props of §3). It gives:
- `FxRepositoryRoot`, `FxWorkspaceRoot` (the highest workspace on disk), `FxRepositoryName`, `FxRepositoryFullName`
  (`/fuxion/plus`), `FxIsCi` (on a CI server).
- The import of `_fx/dotnet/dotnet.g.props` (before the project file) and `_fx/dotnet/dotnet.g.targets` (**right after it**, through
  `BeforeMicrosoftNETSdkTargets`, before the .NET SDK computes anything: so its targets see what the `.csproj`
  declares and can still set `OutputType`).
- **Version from git** (§6) and **static metadata** (`Fuxion.Metadata.<Project>.{Project, Build, Versioning,
  Repository, Json}`), `FxVersioningEnabled`, `FxStaticMetadataEnabled`.
- **`FxReference`** (§5) and the error `FXTL001`.
- Translated XML documentation (`FxDocumentationLanguages`: copies the English XML to `~$docs/en` and packs
  `~$docs/<lang>/<Assembly>.xml`). No Fuxion repo uses it now (plan R: the documentation module is to be rethought).
- fx's local files and folders (`~$…`) out of the projects' default globs.

Local publishing is not the SDK's: the workspace's `packable.props` sets `PackageOutputPath` to
`<workspace>/~$publish/<repo>/nupkgs` (or `<repo>/~$publish/nupkgs` in a clone on its own).

The settings are listed at the top of `tool/repo/solution/src/Tool.Sdk/Sdk/Sdk.props`. The SDK's error and warning
codes are the area `FXTL` (`FXTL001`-`099`), reserved in oss's `DiagnosticIds.cs` next to the analyzers' `FX…` areas.

## 3. The shared build: `_fx/dotnet/dotnet.yaml` of the workspace

Three different things (plan N, decision 15):

- **Variables**: the tool defines them, projects use them. `value:` gives a property (`$(CoreFrameworks)`); `when:`
  gives a `true`/`false` property computed per target framework (`$(IsNet11)`), with optional `define:` compilation
  constants for `#if`.
- **Properties of the repo**, standard .NET ones (`IsPackable`, `IsTestProject`, `OutputType`…): the project or its
  `Directory.Build.props` sets them, as always.
- **Imports**: which plain MSBuild files of `_fx/dotnet/` (paths relative to it) go into which projects. `props:`
  before the project file (they cannot see what the `.csproj` sets), `targets:` right after it (they can); `when:` on
  a variable, a property of the repo, or nothing (every project); `applies-to:` (tags or repositories) for some repos
  only, as variables and packages can too; `files:` what travels with an import without being imported (the
  `icon.png` of `packable.targets`). A repo gets only what is for it, and only the files of those imports (plan R):
  a file of `_fx/dotnet/` that no import names is a warning of `fx doctor`.

Today's imports (`_fx/dotnet/`):

| File | Where | What |
|---|---|---|
| `default.props` | every project | `LangVersion preview`, `Nullable enable`, `ImplicitUsings disable`, warnings as errors (and nullable ones), code style in build, `IsPackable=false` by default, `ContinuousIntegrationBuild` on CI. Only what the project has not set |
| `packable.props` / `.targets` | `IsPackable=true` | XML docs, symbols (snupkg), author, product, `fuxion.dev`, `PackageOutputPath` (local publishing); `PACKAGE_README.md` and `icon.png` (`files:` of the import) in the package |
| `package-oss.targets` | `IsPackable=true` and `FuxionPackage=oss` (the area or the project says it) | the MIT license; the repository comes from git (SourceLink) |
| `package-plus.targets` | `IsPackable=true` and `FuxionPackage=plus`; only in the private repos (`uses-fuxion`) | the proprietary license, `plus/LICENSE.txt` (`files:`), which the user accepts |
| `test.targets` | `IsTestProject=true` | `OutputType=Exe`, `xunit.v3`, `Microsoft.Testing.Extensions.CodeCoverage` |
| `polysharp.targets` | `netstandard2.0`, `net472` | PolySharp |
| `fuxion-analyzers.targets` | repos tagged `uses-fuxion` and `oss`, unless the project says `UseFuxionAnalyzers=false` (the analyzer projects themselves) | the analyzers of oss (§5), and their dlls for Visual Studio's live analysis |
| `pack-analyzers.targets` | `oss`, `IsPackable=true` | the analyzers inside every package of oss (`analyzers/dotnet/cs`) and `Fuxion.Analyzers.Abstractions` in `lib/`, from the map of the repository |

### Target frameworks and constants

Projects never write framework names; they use the variables:

| Variable | Value |
|---|---|
| `DefaultFrameworks` | `netstandard2.0;net472;net10.0;net11.0` |
| `CoreAndOldFrameworks` | `net472;net10.0;net11.0` |

`STANDARD_OR_OLD_FRAMEWORKS`. Use the conditions in item conditions of a `.csproj`
(`Condition="'$(IsOldFrameworks)' == 'true'"`); they are computed after the project file, so not in its properties.

## 4. Package versions

Central Package Management (`ManagePackageVersionsCentrally` + `CentralPackageTransitivePinningEnabled`) in every
repo. Every package version is in one place (user, 15-oct), never also in a repo (D-16; NuGet rejects it, and
`fx doctor` explains it):
- **The workspace's `dotnet.yaml`** (`packages:`, in alphabetical order; the .NET platform, EF Core and MongoDB EF
  Core at the end, with a version per framework; `Fuxion` 10.0.18 only for `tool`, which uses it by package). fx writes
  the ones the repo uses (also through an `FxReference`) in `_fx/dotnet/packages.g.props`, which the repo's
  `Directory.Packages.props` imports (or, in a repo without central management, as `PackageReference Update` in
  `dotnet.g.targets`). With several versions, each needs its `when` (D-32: every framework gets exactly one;
  `fx doctor` checks it); a single version is for every framework. **To upgrade one, change the yaml and `fx sync`.**
- **The repo's `solution/Directory.Packages.props`** only imports `packages.g.props`. fx writes there only what the
  repo references directly: a version that only arrives transitively (the `System.Security.Cryptography.Pkcs` of the
  vulnerability of `Microsoft.Data.SqlClient`) is not pinned in a repo that does not reference it (plan R, finding).
- `PackageReference` never carries `Version=`.
- oss's `solution/test` adds `NU1902;NU1903` to `NoWarn` (the vulnerable `System.Security.Cryptography.Pkcs` that
  `Microsoft.Data.SqlClient` brings, which fx does not pin there: see above); everywhere else warnings are errors.

## 5. References between projects

- **Inside a repo and to another repo**: `<FxReference Include="Fuxion" />`, by project name, never a path (plan R).
  A project of the same repo is a `ProjectReference` through the map of the repo (`_fx/dotnet/projects.g.props`,
  generated and versioned, so it works in a clone on its own too); one of another repo, in the workspace, is a
  `ProjectReference` (whichever solution is open, design D-13: the map is `_fx/dotnet/~$workspace.props` of the
  highest workspace on disk, written by `fx sync`); outside it, a `PackageReference` (its version in the repo's
  `Directory.Packages.props`, or the workspace's `dotnet.yaml`).
  `FxUsePackages=true` makes those of other repos packages (a CI); those of the same repo are always projects.
- **`WorkspaceOnly="true"`** on an `FxReference`: only in the workspace, nothing outside it (the analyzers of oss,
  which the `Fuxion` package already carries).
- A repo that only builds inside the workspace (`next`, `archive`, `lab`: not `standalone`) gets
  `FxRequiresWorkspace=true` from fx, in its `dotnet.g.props` (plan R): an `FxReference` that is not mounted is error
  `FXTL001`. `fx doctor` checks that a `standalone: true` repo (its own
  `_fx/dotnet/dotnet.yaml`) references nothing from a repo that is not.
- `plus` references `Fuxion` with `PrivateAssets="none"`, so its packages give their users the analyzers (they come in
  the `Fuxion` package).

## 6. Versioning

From git, by the SDK at build time (and `fx version [--explain]` from the command line): the last `version/X.Y.0` tag
gives major and minor, the commits give the patch, one rule per branch kind (`main`/`master`: `X.Y.n`; `feature/x`:
`X.Y.n-feature.x.m`; `develop`, `release/*`, `preview/*`, others). The stable branch is the local `main`/`master`,
else `origin/main`/`origin/master`, else HEAD. Base tags: `oss` `version/10.1.0`, `plus` `version/10.0.0`, `next`,
`archive`, `lab` `version/11.0.0`, `tool` `version/0.2.0` (local, 12-oct: the layout of plan P). `fx version tag X.Y`
creates a new base (local; push it yourself). `FxVersioningEnabled=false` turns it off.

## 7. Test projects

- **A test project says so in its `.csproj`**: `<IsTestProject>true</IsTestProject>`. The workspace's `test.targets`
  makes it an executable (`OutputType=Exe`) with `xunit.v3` and the coverage package: a test `.csproj` declares no
  test package at all.
- Projects in `test/` that are not tests do not say it: helper libraries (`Test.Dataset*`, `Test.Responses.Shared`,
  `Test.Responses.Shared.Fixtures`) set `<OutputType>Library</OutputType>`; `Test.AspNetCore.Service` (the host of the
  ASP.NET Core tests) sets `<IsTestProject>false</IsTestProject>`.
- **`xunit.analyzers` is on** (plan I) and, with warnings as errors, its rules break the build. The usual one is
  xUnit1051: pass `TestContext.Current.CancellationToken` to every call that accepts a token (use `ct:` by name for
  Fuxion's `AsResponseAsync(jsonOptions, ct)`). For multi-target tests, `Fuxion.Xunit` adds on .NET Framework the
  token overloads net472 lacks (`ReadAsStringAsync`, `ReadAsByteArrayAsync`, `ReadAsStreamAsync`, `ReadToEndAsync`,
  `CopyToAsync`), so the same call compiles on every TFM. `Test.Responses.Shared` (a library of `[Fact]` families)
  references `xunit.analyzers` itself.
- `Fuxion.Xunit` is a plain library: `xunit.v3.extensibility.core` + `xunit.v3.assert` (never `xunit.v3`, which would
  turn it into a test executable). Other repos reference it with `<FxReference Include="Fuxion.Xunit" />`.
- There is no VSTest infrastructure (no `xunit.runner.visualstudio`, no `Microsoft.NET.Test.Sdk`): tests run on
  Microsoft.Testing.Platform (every `global.json` says `"test": {"runner": "Microsoft.Testing.Platform"}`), and Visual
  Studio's Test Explorer and ReSharper run them as such.
- Run them from the folder of a solution: `dotnet test --solution Fuxion.slnx` (the workspace root, or `oss/repo`),
  `dotnet test --solution FxPlus.slnx`…, or `--project <absolute path>`. Test executables can also be run directly:
  `bin/Debug/<tfm>/Test.Xxx.exe -class "Full.Name"`.
- **Coverage** comes from `Microsoft.Testing.Extensions.CodeCoverage` (`--collect "XPlat Code Coverage"` and
  `coverlet.collector` are VSTest and do nothing on MTP). One run per project and TFM, plus a merged report:
  ```bash
  dotnet test --solution Fuxion.slnx --coverage --coverage-output-format cobertura --results-directory <dir>
  perl .claude/skills/build-system/coverage.pl <dir>/merged/merged-*.cobertura.xml 'src.Fuxion.Response' --ranges
  ```
  `coverage.pl` aggregates by file (line and branch coverage, biggest gaps first; `--ranges` lists the uncovered
  lines). Use a results directory outside the repos (for example under `%TEMP%`).
- **Tests with databases** use Testcontainers and need Docker Desktop running (`next/test/Linq`: SQL Server and, on
  net10 only, MongoDB; `plus/test/EntityFramework`: SQL Server). Their fixtures are xUnit
  collection fixtures with `IAsyncLifetime`, random host ports and no container reuse, so projects never collide.
- **Everything is green**: 6532 tests in oss, plus, next, archive and lab (6480 passed, 52 skipped). Anything out of
  scope is skipped with a reason that names its idea (`Skip = "… (idea I-NN)"`, `SkipWhen` for a single TFM,
  `Assert.SkipWhen` inside shared test bases). A new red test is a real failure, never "the usual ones".

## 8. Checklist

- **New package:** its version in `packages:` of the workspace's `_fx/dotnet/dotnet.yaml` (every package is there,
  in alphabetical order; `applies-to` if it is only for some repos) and `fx sync`.
  Then `PackageReference` without version in the `.csproj` (or in a shared props if every project of a kind needs it).
- **New project:** folder in the repo's `solution/` → `.csproj` with `$(…Frameworks)` and `FxReference` by name
  (inside the repo too, plan R); `FuxionPackage` if it is a package of another kind than its area → `IsTestProject=true` if it is a test → add it to the repo's
  solution → `fx sync` (the workspace's `Fuxion.slnx` and the map pick it up).
- **New repo**: `fx repo add <url> <path> --tag dotnet --tag fuxion-build` (and `uses-fuxion` if it uses Fuxion);
  its solution in the `solutions` of the workspace's `_fx/dotnet/dotnet.yaml`; `global.json`, `Directory.Build.props`
  importing the SDK and its `Directory.Packages.props`; `fx sync`.
- **Change the shared build** (a default, a framework, a shared version): the workspace's `_fx/dotnet/dotnet.yaml` or
  its files, then `fx sync`, and commit the changes it makes in each repo.
- **Verify:** `dotnet build Fuxion.slnx` at the workspace root (everything, 0 warnings) **and**
  `dotnet build Fuxion.slnx` in `oss/repo` (oss alone); `fx doctor`.

## 9. The `tool` repo (`tool/repo`, plan K)

Since 06-oct-2026 the tool lives in its own repo, `Fuxion-tool`, mounted at `tool/repo` (the frozen copy that
versioned the `plus` build was removed in phase 4, plan N).
- `FxTool.slnx` at the repo root (design D-33), projects in `solution/src` (`Fuxion.Tool`, the `fx` executable;
  `Fuxion.Tool.Core`; `Fuxion.Tool.Sdk`, the MSBuild SDK) and the tests in `solution/test/Tool.Test` (also in the
  workspace `Fuxion.slnx`).
- **`Fuxion.Tool.Sdk`** (stage K3, see its README section and the settings at the top of `Sdk/Sdk.props`): pinned in
  a repo's `global.json` (`msbuild-sdks`) and imported in `Directory.Build.props` with
  `<Import Project="Sdk.props" Sdk="Fuxion.Tool.Sdk" />` after the area's `Fx*` properties. **Minimally intrusive**
  (design D-37, plan N decision 15): only its own features (where the repository is, version, metadata, `FxReference`,
  what `dotnet.yaml` generates, translated docs); no language defaults, test frameworks, packaging metadata or where
  the packages go. It hooks itself in three places: `BeforeMicrosoftNETSdkTargets` (right after the project file, before
  the .NET SDK computes anything: `dotnet.g.targets`), `CustomBeforeDirectoryBuildTargets` and `CustomAfterMicrosoftCommonCrossTargetingTargets`
  (the late part, also in the outer build that packs), keeping whatever each one had. Its tasks use `UsingTask … Runtime="NET"` (the .NET task host under Visual Studio)
  and target `net11.0`, as the MSBuild they build against (18.11, the line of .NET 11): the SDK needs the .NET 11 SDK, and in Visual Studio
  18.11 or later (18.10, the one of the GitHub runners in October 2026, cannot load the tasks; its test is skipped there);
  `Core` too (it is no package: inside the exe of `fx`, and copied to `tasks/` of the package of the SDK). A local
  package needs a new version each time: NuGet caches by version.
- `fx` is published with **native AOT** (`PublishAot`, `InvariantGlobalization`; `Core` has `IsAotCompatible`, so its
  analyzers turn any trimming or AOT problem into a build error). Keep it so: no reflection (JSON through
  `JsonSerializerContext`), no packages that are not AOT-compatible. Publish with
  `dotnet publish tool/repo/solution/src/Tool/Fuxion.Tool.csproj -c Release -r win-x64 -o <folder>`; from Git Bash,
  add `C:\Program Files (x86)\Microsoft Visual Studio\Installer` to the `PATH` first (the linker calls `vswhere.exe`).
- `fx` reads git only through the `git` executable (`GitClient`, on `ProcessRunner`); no LibGit2Sharp.
- **The layout fx works on** (plan P; the tool README has the summary): `_fx/` anchors a root of fx, with a folder
  per module (`_fx/workspace/workspace.yaml`, `_fx/dotnet/dotnet.yaml`, `_fx/harness/harness.yaml`), `_fx/fx.yaml`
  (name, `requires`, catalog of tags) and `_fx/.inherited/` in what hangs from a workspace. The code: `Tool.Core/Layout`
  (the fixed paths, the header, `schema`, `applies-to` and full names, `fx.yaml`, `inherited.yaml`), `Tool.Core/Sync`
  (the engine: `SyncEngine` and `Inheritance`), `Workspace`, `Dotnet` and `Harness` (plan Q: the rules and skills of
  the coding agents, which generate `AGENTS.md`, `CLAUDE.md` and the skills of every root; the header only counts at the
  top of a file, or right after the front matter of a Markdown file).
- **`_fx/dotnet/dotnet.yaml`** (stage K4; plan P): `fx sync` generates `_fx/dotnet/dotnet.g.props` (who the repo is,
  value variables and the `props:` imports, imported by the SDK's `Sdk.props`), `dotnet.g.targets` (when variables,
  constants and the `targets:` imports, right after the project file) and the package versions: with central package
  management, `_fx/dotnet/packages.g.props` (imported by `Directory.Packages.props`); without it, `PackageReference
  Update` in `dotnet.g.targets`, and keeps `msbuild-sdks` of `global.json` exactly as `sdks:` (the key is fx's: an SDK
  that leaves `sdks:` leaves it too; also in the workspace's when it composes `solutions`: MSBuild reads `msbuild-sdks`
  from the folder of the solution, so `Fuxion.slnx` builds every repo with the root's pin, not each repo's);
  `fx doctor` checks them, D-16, D-32 and the
  versions in `Directory.Packages.props` that no project uses, directly or transitively (`dotnet.unused-package`, from
  the last restore). Never edit the `.g.` files: change the yaml and run `fx sync`. YAML is read with SharpYaml's
  parser into fx's own tree with 1-based positions (`Tool.Core/Yaml`, plan O decision 11; AOT, no reflection). A `when`
  variable can also `define:` compilation constants (`OLD_FRAMEWORKS`), written to `dotnet.g.targets` with the expanded
  condition (plan N, decision 1). The `imports:` section says which plain MSBuild files of `_fx/dotnet/` go into which
  projects (`props:`, `targets:`, `when:`, `applies-to:`); the workspace's `_fx/dotnet/` reaches the repos of its
  `applies-to` in their `_fx/.inherited/dotnet/`, merged with what the workspace itself inherits (plan P, decisions
  14-16), and `inherited.yaml` keeps who the repo is (name, full name, tags: for a clone outside the workspace) and
  where each file comes from. A package with a single version may omit `when` (for every framework).
- **`FxReference`** (design §6, plan N): `<FxReference Include="Fuxion" />` names a project of another repo.
  In a workspace, the SDK imports `_fx/dotnet/~$workspace.props` of the highest workspace on disk (written by
  `fx sync`: one `FxWorkspaceProject` and one `ProjectReference` per project versioned in the mounted repos, built from
  the `FxReference` so it keeps its metadata) and it is a project; otherwise it is a `PackageReference` (version from
  `Directory.Packages.props`).
  `FxUsePackages=true` makes them all packages; `FxRequiresWorkspace=true` (a repo that only builds in the
  workspace) turns a missing one into error `FXTL001`; `WorkspaceOnly="true"` on the item means "only in the workspace"
  (the analyzers of `oss`, which its packages carry).
- It builds with **its own SDK** (15-oct-2026), like the other repos: tag `fuxion-build` in the manifest,
  `standalone: true` in its own `_fx/dotnet/dotnet.yaml`, and the conventions and package versions of the workspace's

- It uses Fuxion **by package** (10.0.18, the last published) instead of linking oss source files: the `Fuxion`

- `solution/sketches/NugetPackageManager` needs Fuxion 11 and is in no solution. The old `Fuxion.Tools` of `plus` (its

- **The name** is `Fuxion.Tool` since 0.6.0 (plan R, step R5; before it, `Fuxion.Tools`): the package of `fx`, the SDK

  throwaway git repos with the real `git` (`TempGitRepository`, isolated from the user's git configuration) and run
  the CLI in process (`InProcess.Run`). The classes run in parallel (I-44: about 3.5 minutes instead of 15 on Windows,
  where every `git` is a process that costs); what changes the process (environment variables: `CI`, `FX_CACHE`,
  `FX_WORKTREES`; the language) goes to the collection `ProcessCollection`, alone, after the rest. A class of the sample
  tree costs about 10-20 s per test (each builds its git repositories): split a heavy one rather than make it parallel
  inside. `fx ui` is tested on a terminal in memory (`UiTree`, `UiTest`, `UiActionTest`): keys pushed, the screen read
  back with `TestScreen`; XenoAtom has one dispatcher per process, so while the app is open it takes the gate of
  `InProcess` alone, and the command line shares it.
- Verify with `dotnet build tool/repo/FxTool.slnx` and `dotnet test --solution tool/repo/FxTool.slnx`. CI
  (`.github/workflows/ci.yml`): build and tests on Windows and Linux, `fx.exe` as an artifact; it publishes nothing.
  Still **off** (only by hand); turning it on is the next step. It needs the `version/*` tags on GitHub.
- **Local publishing** (stage K5, design D-36): `tool` versions itself from its `version/X.Y.0` tags (with its SDK, as
  `fx version`); `fx.exe` goes to `<workspace>/~$publish/tool/fx/win-x64/` and `Fuxion.Tool.Sdk` to
  `<workspace>/~$publish/tool/nupkgs/` (its `packable.props`; commands in the tool README). The workspace root has a
  local, unversioned `nuget.config` with those folders as sources (like `Fuxion.slnx`), so every mounted repo restores
  the local SDK. Publish only from a clean commit: a new version each time. For **nuget.org** (the user publishes),
  pack as CI (`CI=true dotnet pack …`: deterministic, no `+local` in the informational version) from a commit that is
  on GitHub (SourceLink points to it), push the same package to the local feed, and raise `sdks:`.
